## 2026-11-03 morning: prefixgate (streaming typed decision model as LTT policy gate on growing prefixes)

Rule: no GPU spend. Everything below runs on CPU (HF ZeroGPU or a free CPU Space only for the demo).

Repo name: prefixgate
GitHub topics: ai-frontier-research, decision-models, agent-guardrails, conformal-prediction, tool-calling, streaming, system-one, cpu-inference, typed-decisions

Signal: decision-policy-gates (new watch, 0.40) plus act-while-listening (0.40) and rsi-harness (0.55). Papers: Decision Models as Policy Gates (https://arxiv.org/abs/2611.02155v1), Ranked but Not Stopped (https://arxiv.org/abs/2611.02522v1), Local or Escalate (https://arxiv.org/abs/2611.01639v1), Flide (https://arxiv.org/abs/2610.42148v1), LeanGuard (https://arxiv.org/abs/2611.02332v1, hard Lean baseline); product: Sage2 (https://x.com/levantolabs/status/2117304026911908020, vendor claims unverified).

Idea: Policy Gates scores a finished tool call once. Local or Escalate routes at a single listen-to-speak frame. forecall (already proposed) dispatches candidate tools early. prefixgate instead re-scores allow / deny / escalate at every growing PREFIX of a tool-call argument stream (or of a user utterance that will become a call), with a Learn-then-Test guarantee on false-allow and false-deny rates. At each prefix length t (token or 200 ms ASR chunk), a small typed decision model over the fixed option set {allow, deny, escalate} reads the policy text, the tool schema, and the prefix so far, and returns calibrated probabilities. LTT (Angelopoulos et al. 2021) picks score thresholds on held-out data so that the false-allow rate is at most alpha_a and the false-deny rate is at most alpha_d with probability 1 - delta. Deny is fail-closed; escalate hands the full call to a prompted LLM judge or to LeanGuard-style check (optional, stubbed). The final gate on the complete call must match a batch Policy-Gates baseline so that only when the decision is made changes, not what is allowed.

Why new (closest prior work): Decision Models as Policy Gates (2611.02155) evaluates hosted DMs on completed tool calls, not streaming prefixes; Local or Escalate (2611.01639) is a duplex speech path router at one transition, not a tool-policy gate; Ranked but Not Stopped (2611.02522) ranks hijacks from DM confidence but does not gate tools; Flide (2610.42148) speeds DM inference via state forking; LeanGuard (2611.02332) is a hard Lean runtime, not a soft streaming DM; SHIFT-JEV (https://arxiv.org/abs/2610.34329v1) is abstention under distribution shift; forecall dispatches speculative tools rather than gating them; certified runtime safety for tool agents (https://arxiv.org/abs/2607.22868v1) is theory, not a streaming DM. Novelty searches on the arXiv API (streaming + decision model; prefix + guardrail + tool call; typed decision + gate), GitHub search (prefixgate / streaming decision / decision gate agent) and HF papers search found no work that applies an LTT-calibrated typed decision model to growing prefixes of tool calls.

Hypothesis (falsifiable): on a held-out set of real tool-call transcripts with injected unsafe prefixes (built from the Policy Gates style rule set, labeled once by hand, no mock labels), (1) LTT-calibrated prefixgate keeps false-allow and false-deny rates inside their alpha bounds (empirical rate inside the binomial 95% interval of alpha); (2) at matched false-allow rate, the median decision lead (tokens or ms of prefix before the final batch gate would have fired the same decision) is larger than the batch-only Policy Gates baseline, with a 95% bootstrap CI that excludes 0. It fails if either bound is violated, if the CI includes 0, or if a simple entropy threshold on a prompted classifier matches the lead.

Experiment (real runs only, CPU):
1. Data: build a tool-call prefix corpus from public agent traces. Prefer the open ToolBench / API-Bank style call strings already used in literature, or regenerate calls with Qwen2.5-0.5B-Instruct against a fixed 12-tool schema (file read/write, shell, http get/post, send_message, delete) under the 28-rule spirit of Policy Gates (write the rule list in RULES.md once). Inject unsafe suffixes and mid-prefix hijacks from the five FlipJev / Ranked families (copy, do not invent attack text beyond those papers' published templates). Seed and size the set to the compute cap; state N_train, N_cal, N_test in the README. No mock labels: every (prefix, gold gate) pair is either a real completed call truncated or a published attack template applied to a real call.
2. Decision model: train a LoRA typed-decision head on Qwen2.5-0.5B-Instruct (Apache-2.0) or use flan-t5-base (Apache-2.0) with a three-way classification head over allow/deny/escalate. Train on completed calls and random proper prefixes with the gold final label (ponytail: one head, one loss).
3. Calibration: LTT over a grid of (allow_threshold, deny_threshold) on the calibration split; alpha_a in {0.02, 0.05}, alpha_d in {0.05, 0.1}, delta 0.1.
4. Baselines: batch Policy Gates (score only the full call); prompted Qwen2.5-0.5B yes/no/escalate; entropy threshold on the DM; Local-or-Escalate-style single-frame logistic on hidden states at 50% prefix (ablation).
5. Metrics: false-allow, false-deny, escalate rate, median/mean lead (tokens and wall ms), AUROC of allow-prob for unsafe vs safe prefixes, every run including negatives, CPU model and wall time.
6. Demo: app/server.py (stdlib http.server) + app/index.html: replay a real call with a growing prefix strip, live allow/deny/escalate bars, lead clock, and a mic or paste mode that streams typed text. No tools are actually executed in deny/escalate paths.

Compute (CPU only, no GPU spend): target one 8-core / 16 GB RAM box, torch CPU, 8 threads. Estimate (measure and replace in README on first run): flan-t5-base or Qwen2.5-0.5B forward ~0.3-0.7 s per prefix on CPU; 200 prefixes x 200 test calls ~= 4-8 hours if naive; skip unchanged prefixes and batch across calls so the full cal+test loop fits in at most 12 hours wall time. LoRA or head training: time 100 steps first on CPU, report wall time, cap at 4 hours. Whole experiment (data prep, train, LTT, test, plots, demo GIF) fits in at most 16 hours wall time on one 8-core 16 GB CPU machine. No paid cloud, no GPU.
